# How the Sharpa sim-state verifier decides success

This document explains every rule the verifier uses, where it lives in the code (click the pointers), why each
threshold has the value it has, and how sensitive the labelled results are to it. It is generated by
`_build_logic_doc.py` from `VERIFIER_LOGIC.template.md`; re-run the generator after a code change so the pointers
stay exact.

## 1. The pipeline in one page

- **Task specs.** Each task (scene) has an ordered list of stages, written in {{_build_task_specs.py::^S = \{}} and
  compiled to `task_specs.json` by {{_build_task_specs.py::^def main}}. A stage is a dict: `check` names the check
  function, the other keys are its parameters. Parameters not set in the spec fall back to defaults written in the
  check function (`s.get("key", default)`), so the effective threshold is "spec value if present, else default".
  Small helpers build the common stages: {{_build_task_specs.py::^def reach}}, {{_build_task_specs.py::^def grasp}},
  {{_build_task_specs.py::^def pick}}, {{_build_task_specs.py::^def place}}, {{_build_task_specs.py::^def pour}}.
  Tasks that cannot be graded are listed in {{_build_task_specs.py::^SKIP = \{}}.
- **Checks.** The registry {{verify.py::^CHECKS = \{}} maps names to functions. The tool-use checks live in
  `tool_verifiers/` and are added to the same registry at import ({{tool_verifiers/__init__.py::^def register}}).
  Every check returns `(mask, metrics, conds)`: a per-frame boolean "this stage is satisfied at frame i", raw numbers,
  and the named conditions whose AND is the mask.
- **The chain.** {{verify.py::^def verify}} runs the stages in order. A stage only counts from the frame its predecessor
  was first satisfied (retries are allowed: the chain restarts from the latest first-success frame). A stage with
  `final: True` is graded on the **last frame** (end state: still in the pan, lid still closed, not dropped); otherwise
  it is graded on **any time** after its predecessor. The episode passes when every stage passes and no object listed in
  `no_fall` fell off the table.
- **Why it failed.** Each condition's name carries its threshold and the measured value. For a failed stage,
  {{verify.py::^def why_failed}} lists the conditions that were false at the graded frame (or never true together), so
  the explanation reads "standard (measured)". Compound tool checks write one line that starts with the failing
  requirements, e.g. `stirred - FAILED: reaching 0.046 m below the rim (needs >= 0.06 m). ok: ...`.
- **Labels and calibration.** Labelled teleop recordings live in `data/webxr_episodes/<task>/<label>_<id>/`, labels
  `success`, `recover` (succeeded after a retry: counts as success) and `failure`. They are verified on the **full**
  recording (what the labeller watched); policy rollouts are cut at the task time limit (`limits.py`).
  {{calibrate.py::^def main}} compares verdicts with labels; the reviewer's decisions in the disagreement viewer
  (`_viewer/reviews.json`) correct labels: "verifier right" replaces the label with the verdict shown at review time,
  "human right" keeps the label, "both wrong" / "unsure" leave the episode out ({{calibrate.py::^def load_reviews}}).
- **Scores.** `score.py --grader hybrid` grades policy rollouts with the verifier (the vision judge is no longer used
  by any active task).

## 2. Shared building blocks

- **Replay** ({{verify.py::^class Replay}}): replays the recorded joint positions frame by frame in MuJoCo and stores,
  per frame, every object's pose, hand-object contact (and the contact points in the object frame, for "which part is
  held"), the wrists, finger flexion, finger segment positions, and the contact pairs between bodies.
  Units: metres, seconds; one frame = `DT` = 0.05 s.
- **Holding** = hand-object contact with gaps of up to 3 frames (0.15 s) bridged ({{verify.py::^def fill_gaps}}): a
  hand loses and regains sim contact constantly while holding.
- **Lift** is measured at the object's **lowest point** above its start height ({{verify.py::def lift_bottom}}), so
  tipping one end up is not lifting.
- **held(mask, s)** ({{verify.py::^def held}}): true from the frame where mask has been true for s seconds in a row.
- **Rotated footprints.** "Inside the target" uses the target's own box on its two most horizontal axes
  ({{verify.py::def in_target}}), not the world-axis box, which grows when the target is turned (a case turned 45 deg
  covered the table beside it).
- **Tool-target contact parts** ({{tool_verifiers/common.py::^def tool_target_contacts}}): contact points between two
  objects, expressed in both objects' frames, so a check can ask "did the hammer **head** touch the box", "did the
  eraser touch the plate's **face**, not its rim" ({{tool_verifiers/common.py::^def part_contact}}).

## 3. Shared rules

### Reach and grasp
- **reach** ({{verify.py::^def c_reach}}): a hand within 3 cm of the object.
- **grasp** ({{verify.py::^def c_grasp}}): hand contact for 0.4 s while the object is lifted >= `lift_m` (default 3 cm)
  or carried >= `carry_m` (5 cm).
- **hold lifted** ({{verify.py::^def c_hold_lifted}}): lifted >= `lift_m` with contact for `hold_s` in a row. Options:
  `grasp_box` (contact must be on a handle region, e.g. the drill), `finger_holes` (scissors: thumb through one ring
  and the index through the other, {{verify.py::def fingers_in_holes}}).

### The drop rule (one detector for every task)
{{verify.py::^def _release_event}} looks at a release: the hand loses contact while the object's origin is >= 3 cm up.
It first decides whether the release was **deliberate** from the hand: fingers opening (flexion rate <= -0.10 rad/s)
or wrist lowering (<= -0.06 m/s), and the hand not shooting up (>= 0.15 m/s). Then, with h = the release height of the
object's lowest point, the release is a **drop** if any enabled clause fires:

| clause | fires when | default | switch off |
|---|---|---|---|
| slipped out | h >= `drop_min_height_m` (2 cm), not deliberate, and the object then comes down >= 0.3 m/s | on | `slip_fall_m_s: None` |
| let go too high | h >= `drop_height_m` (20 cm; placements: 30 cm above where it landed) and it falls >= 0.5 m/s, however the hand moved | on | - |
| tumbled | it turns > 70 deg on its own after the release (a deliberate release from below `tumble_deliberate_min_m` is excused) | on | `tumble_deg: None` |
| ended tipped over | it ends > 45 deg from its start tilt after a release that was not deliberate | on | `end_tilt_deg: None` |

The explanation states each clause with measured value and limit, the one that fired first (code just after
{{verify.py::# explanation: the verdict first}}).
The **last** release is judged to the end of the recording. When a task counts drops at **every** release
(`max_drops_while_working`, scramble), each release is judged only up to the next regrasp, so a later fumble does not
count against an earlier release ({{verify.py::a release is judged up to the next regrasp}}). Releases are enumerated by
{{verify.py::^def _release_frames}}.

- **Not dropped at the end** ({{verify.py::^def _not_dropped}}): if the object is still in the hand at the end (contact,
  lowest point >= 2 cm up; shakes accept "touching for the last 0.5 s at any height") it passes; otherwise the last
  release must not be a drop, it must not end below its start height or off the table, and (where set) it must stand
  upright.
- **Placements and pours** use only the "let go too high" clause, measured above where the object landed
  ({{_build_task_specs.py::^DROP_END_GRADED}}): labelled placements count objects that slip out 5-15 cm above the target
  and land inside as done.

### Not flung, not toppled (after the last release)
{{verify.py::^def _not_flung}}: after the hand lets go for the last time the object never moves faster than
`max_free_speed_m_s` (a throw, a toss, a box flying off, a tablet falling flat at speed), and, where set, never turns
more than `max_free_rot_deg` on its own (a tablet stood on its edge that tips over slowly). Only the last release
counts: an object that got away and was picked up again is a recover.

### Placements, removal, pours
- **place in** ({{verify.py::^def c_place_in}}, shared logic in {{verify.py::^def _placed_common}}): at the end the object
  is inside the target (rotated footprint, height band), released, at rest, and (option) touching it.
- **move out** ({{verify.py::^def c_move_out}}): out of the container's rotated footprint; `min_disp_m: 0` = being out is
  enough.
- **pour** ({{verify.py::^def c_pour}}): tilted >= 30 deg with the pouring lip (the rim on the low side,
  {{verify.py::def lip}}, or a spout tip) **inside** the target opening (no slack by default), within 5 cm below to 25 cm
  above it, in hand, for `hold_s` (0.1 s); optionally tipped **toward** the target (`toward_target_m`: the low rim nearer
  the opening's centre than the container's body). Afterwards held or set down upright, the target not knocked over or
  pushed away, and no collision (the poured object touching the target while moving > 0.7 m/s).

### Rotations, flips, shakes, articulated objects
- **orientation** ({{verify.py::^def c_orientation}}): flip (start-up axis points down), rotate (angle from start),
  face (an axis points toward a direction), axis_away (portrait). Flips limit in-hand speed and lift; travel from the
  start is not limited (reviewer: "this should not be the condition of upturn"). Rotations graded at the end
  (`end_rule: not_dropped`, 01541) need the goal pose **held for 0.5 s** at some point, and the speed / travel / lift
  limits stay episode-wide conditions, so moving the object too far after reaching the pose still fails
  ({{verify.py::rotate / flip tasks graded at the end: the goal pose held}}).
- **oscillation** ({{verify.py::^def c_oscillation}}): shake = >= 3 direction reversals of >= `min_amp_m` within 3 s
  while held, then the ending rules.
- **joint goal** ({{verify.py::^def c_joint_goal}}): laptop, doors, lids: the joint reaches the goal, gently
  (`max_approach_speed` near the closed position), upright, not lifted.

## 4. Tool-use verifiers (`tool_verifiers/`)

Shared measurements in {{tool_verifiers/common.py::^"""Shared measurements}}:
- {{tool_verifiers/common.py::^def work_in_target}}: the tool's working point (a point on the tool, or its **lowest**
  point within a part, e.g. the tip of a tilted spoon bowl) inside the target's own box while held. Path = travel between
  consecutive working frames only (moving outside the pot, or while not held, earns nothing). Back-and-forth strokes are
  counted per working session ({{tool_verifiers/common.py::^def stroke_count}}), along its main direction, from motion
  made near the surface only (`stroke_near_m` = 2 cm: brush, within 2 cm of the plate face; scramble, the working box
  grown by 2 cm, i.e. 2 cm beside the pan and up to 5 cm above its rim, because labelled scrambling stirs 2-5 cm above
  the rim), credited when confirmed (cumulative confirmations, with the session's axis fitted on the whole session).
  Task overrides: brush counts strokes of 1 cm (`reversal_amp_m` in its spec), scramble 2 cm.
- {{tool_verifiers/common.py::^def end_rules}}: the shared ending: not flung (a speed limit after the last release,
  not the hand-motion drop rule), target not knocked over, not pushed away, not sent flying (each optional). Brush and
  scramble add the hand-motion drop rule on top where their specs ask for it.
- {{tool_verifiers/common.py::^def handling}}: regrasps and spin, **reported only** (not a pass/fail condition).
- {{tool_verifiers/_work.py::^def work_check}}: stir / scramble / scoop: inside time, path, optional depth below the rim,
  optional strokes, and optional "not dropped more than k times while working" (a separate condition). Drops are
  **retrospective counts indexed by release time**: a release is classified with what happened after it (its fall, a
  tumble) up to the next regrasp, and the count is credited at the release frame.

the camera button (not a joint: graded on a fingertip on the drawn dot while the camera is steady).

## 5. Overfitting audit

How the thresholds were set. Almost every threshold was chosen by looking at the labelled recordings of that task:
the measured value on every labelled success and failure, then a value between them. That is fitting on the
evaluation data, so the question is how much each verdict depends on the exact value. Three checks:

1. **Margin**: how far the nearest labelled success and the nearest labelled failure are from the threshold. A rule
   that separates 3 cm from 7 cm with a 6 cm threshold is robust; one that separates 37 deg from 45 deg with 40 deg
   is not.
2. **Sensitivity**: every tuned threshold re-run at x0.75 and x1.25 (integers +-1) on all labelled recordings of its
   task: how many labels flip. A rule whose result changes a lot under +-25% is fitted to the data.
3. **Provenance**: whether the rule came from a physical reason the reviewer stated (a drop, the wrong part, a pose)
   or only from separating the data.

How to read the table: each task has about 60-90 labelled recordings, and ±25% is a large move for a threshold. A
threshold that changes 1-2 labels at ±25% sits in a gap between successes and failures; one that changes 3 or more
has successes or failures close to it on both sides, so its exact value was fitted to these recordings.

### What the sensitive thresholds mean

- **"Not flung" speed limits** (00787 scramble 1.0 m/s, 00863 hammer 1.2, 00749 stir 1.2, 01041 board flip 1.8,
  01587 plate 1.5). The fastest labelled success after release and the slowest labelled throw are close (scramble:
  0.87 vs 1.04 m/s; hammer: 1.10 vs 1.23). The rule itself is physical (a tool thrown down is a failure, reviewer
  "drops / flies away"), but the exact speed is fitted. Expect some disagreement on new data near the limit.
- **Camera button radius 1.3 cm and steady press 0.2 s** (01477). The button's position was read off a render
  (about (-1.7, +0.3, 3.3) cm); fingertips of successes cluster at its edge, so a smaller radius misses them and a
  larger one admits failures. This is the most data-fitted rule: a real button joint in the scene would replace it.
- **Scramble strokes (2) and path (0.2 m)** (00787). Three strokes or 0.25 m would fail 3-4 successes; the labels
  accept short scrambling.
- **Stir depth 6 cm** (00749). Successes reach 7-15 cm, failures 4.6-5.4 cm: the gap is narrow but on both sides of a
  physical idea (dipped into the pot vs hovering at its opening).
- **Plate not sent flying 1.5 m/s, pan moved 0.4 m** (01587, 00787). Each catches one or two specific failures.

The robust thresholds are mostly the ones with a physical reason and a wide gap: placements, the oriented footprint,
the drop rule's clauses, the rack, brushing on the plate face, the scissors grip, the pour collision limit.


## 6. Known limitations and open cases

- Every threshold was chosen on the same labelled recordings it is evaluated on; there is no held-out set. The
  sensitivity table above is the main guard; a fresh batch of labelled recordings is the real test.
- Per-frame masks are not an online reward. Strokes are counted as they are confirmed, but a session's stroke direction
  is fitted on the whole session; drops are retrospective (classified with what happened after the release, credited at
  the release frame) and bounded by the first and last working frames, known only at the end. The verdict is an
  end-state verdict.
- Strokes count only motion made near the surface (brush: an eraser point within 2 cm of the plate face; scramble:
  the blade inside the pan box grown by 2 cm). Brushing in the labels is touch, sweep just above the plate, touch back,
  so near-surface motion between touches counts; dabbing at different spots with the tool lifted away in between does
  not (tests `test_stationary_touches_are_not_a_stroke`, `test_sweeps_just_above_the_surface_are_strokes`). Requiring
  contact (0 cm) would fail 13 brushing and 3 scrambling successes; 2-5 cm change no label, 1 cm one each.
